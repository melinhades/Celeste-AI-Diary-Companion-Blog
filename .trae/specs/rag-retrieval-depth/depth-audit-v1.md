# RAG 检索层深度审计 v1（professional-depth-drill）

> 阶段定位：**只出审计与执行提示，不写业务代码**。审计通过后再进入实现。
> 目标：不扩功能面，把「检索」这一个已有能力做到领域专业深度。

---

## 0. 选定模块与理由

**目标模块**：`MemoryServiceImpl` 的检索链路

| 入口 | 位置 |
|---|---|
| `searchContext(userId, query, limit)` | `blog-api/src/main/java/com/mszlu/blog/impl/MemoryServiceImpl.java#L299-L348` |
| `getRelevant(userId, userContent)` | 同上 `#L48-L113` |
| `chunkDiary(...)` / `splitChunks(...)` | 同上 `#L245-L295` |
| `cosine(...)` / `parseVec(...)` | 同上 `#L115-L136` |

**为什么选它**（而不是长期记忆、人格一致性、圆桌引擎）：

1. 它是 Madeline「我记得你说过…」这类回应的事实底座——检索错了，人格再对也是编造。
2. 现状是教科书级的表面实现：纯 dense top-k、全表扫、固定阈值、无多样性、无时间性、无词法融合。
3. 属于「同一输入、更深输出」，完全符合不扩功能面的约束。
4. 长期记忆（v1 已做环形缓冲+摘要）、人格检查（已做 3 次重生成）的深度空间已不大；圆桌引擎属功能扩张。

**现状证据（读代码得出，非推测）**：

- 每次检索扫 `memory limit 200` + `diary chunk limit 300` + `lore limit 500`，**逐行 JSON 解析 embedding 后在 Java 里算余弦**，无任何缓存。
- 三个来源共用一个固定阈值 `sim > 0.3`，直接排序取 top `limit`。
- `Memory.importance`、`lastMentionedTime` 在排序中**完全不参与**（importance 只在「兜底不足 5 条」时才用）。
- 无去重：同一事件从多篇日记中重复抽取会同时命中。
- 无查询改写：用户一句「我很烦」直接 embed。
- 分片是贪心攒 110 字、每篇最多 8 片，**长日记后半段直接被丢弃**。
- 检索结果没有候选集/引用记录，无法解释「为什么召回了这条」。

## 1. 顶尖从业者会做什么（而我未要求）

| 维度 | 当前实现 | 他们会多做什么 |
|---|---|---|
| 检索信号 | 纯 dense 余弦 | dense + BM25 词法混合，RRF 融合两路排名 |
| 结果多样性 | top-k 直接取 | MMR 抑制近重复，避免同一篇日记的 5 个片段挤占全部名额 |
| 时间性 | 无 | 指数时间衰减 `exp(-Δt/τ)`，τ≈30 天；2 年前的事不该和昨天同分 |
| 重要性 | 字段存在但不参与排序 | `final = sim × (0.8 + 0.2 × importance/5)` |
| 查询表达 | 原始 query 单次 embed | LLM 改写为 2–3 个子查询 + 会话上下文质心，提升短查询召回 |
| 分数校准 | 三源共用固定 0.3 | 分源 z-score 归一化 + 分源阈值 + 置信度分级（high/medium/low） |
| 语义去重 | 无 | 相似度 > 0.92 判为重复，保留最新/最重要的一条 |
| 分片策略 | 贪心 110 字，最多 8 片 | 语义边界切分 + 相邻片合并 + 片头片尾上下文重叠 |
| 分源配额 | 无，lore 500 条可能淹没 diary | 按来源配额（memory 40% / diary 40% / lore 20%） |
| 检索可观测 | 只记最终结果 | 记候选集、各阶段分数、最终进入 prompt、是否被模型实际引用 |
| 性能 | O(N) 全扫 + 每行 JSON 解析 | 向量常驻内存 + TTL 增量失效 |

## 2. 他们会从哪些更原始的素材开始

| 当前用的（已处理） | 他们要的原始素材 |
|---|---|
| 已抽取好的 `memory.content` 短句 | 原始日记全文 + 原始对话轮次（抽取环节的损失不可逆） |
| 每条记录里存的 embedding JSON 字符串 | 内存常驻 `float[]` + 原始 token 序列（供 BM25 建倒排） |
| 单条当前 `userContent` | 最近 2–3 轮对话拼成的查询质心 + 用户当前触发类型 |
| 固定整数 `importance` | 行为信号：被引用次数、`lastMentionedTime`、是否被用户 resolve |
| 无 | 检索日志：哪些 chunk 真正进了 prompt、模型回复实际引用了哪几条 |
| 贪心 110 字分片 | 段落/句群边界 + 相邻片合并后的完整语义单元 |

## 3. 具体方法与工具（严格在现有技术栈内）

约束：Spring Boot 2.5.0 + 原生 HTML/JS + MySQL；**禁止 Lucene / ES / 向量库 / 新 LLM 提供商**；只用 `AiClient.chat / chat(jsonMode) / embed` + 纯 Java + 现有表。

| 方法 | 具体做法 | 当前没做什么 |
|---|---|---|
| BM25（纯 Java） | 内存倒排索引 `token → chunkIds`，中文按 2-gram，k1=1.2, b=0.75 | 只有 LIKE 降级路径 |
| RRF 融合 | `score = Σ 1/(60 + rank_i)`，融合 dense 与 BM25 两路排名 | 无 |
| MMR 多样性 | λ=0.7 贪心选取：`λ·sim(q,d) − (1−λ)·max sim(d, 已选)` | 无 |
| 时间衰减 | `sim × exp(-Δt/τ)`，τ=30 天 | 无 |
| 重要性融合 | `sim × (0.8 + 0.2 × importance/5)` | importance 未参与排序 |
| 查询改写 | `AiClient.chat(..., jsonMode)` 产出 2–3 子查询，embed 后取均值 | 无 |
| 向量缓存 | `ConcurrentHashMap<id, float[]>` + 10min TTL + 写入时增量失效 | 每次解析 JSON |
| 分源配额 | 先按源各自取 top-N，再按 40/40/20 合并 | 无 |
| 语义去重 | 两两相似 > 0.92 合并，保留最新 | 无 |
| 相邻片合并 | 同 `refId` 且序号相邻 → 拼接为一个 chunk | 无 |
| 检索日志 | 复用 `diary_chat_log.retrieved_chunks / retrieved_scores`，扩展候选与引用标记 | 只记最终结果 |
| 分片策略 | 句群切分 + 每片保留上一片末句（已有雏形），去掉「最多 8 片」的硬截断 | 长日记丢内容 |

## 4. 外部证明（必须是数字，不接受「我觉得」）

| 验证方法 | 目标阈值 |
|---|---|
| 检索金标准集：200 组 `(query, 相关 chunk)` 人工标注 → Recall@5 / MRR / nDCG@10 | Recall@5 ≥ 0.80，MRR ≥ 0.75，nDCG@10 ≥ 0.75 |
| LLM-as-Judge 双盲：旧版 vs 新版各 100 组，相关性 0–5 分 | Δ ≥ 0.8，p < 0.05 |
| 消融实验：依次去掉 MMR / 时间衰减 / BM25+RRF / 查询改写 / 语义去重 | 每项使 nDCG@10 下降 ≥ 0.03 才算有效 |
| 下游忠实度：回复引用检索内容的准确率 / 编造率 | 引用准确率 ≥ 0.90，编造率 ≤ 5% |
| 在线反馈：👍 率对比 | 提升 ≥ 5pp，p < 0.05 |
| 性能：检索 P95 延迟 | ≤ 300ms（当前全扫 + JSON 解析） |

## 5. 分期实施路线（每期独立可回滚）

| 期 | 内容 | 风险 | 预期收益 |
|---|---|---|---|
| **P1** | 向量内存缓存 + 分源配额 + 时间衰减 + 重要性融合 | 低（不改召回集合，只改排序） | 延迟大幅下降，排序更合理 |
| **P2** | BM25 倒排 + RRF 融合 | 中（新增词法链路，需可降级） | 短查询召回显著提升 |
| **P3** | 语义去重 + MMR + 相邻片合并 | 中（改变最终输出集合） | 减少冗余，提升信息密度 |
| **P4** | LLM 查询改写（失败自动回退原始 query） | 中（多一次 LLM 调用） | 模糊查询召回提升 |
| **P5** | 检索日志扩展 + 金标准集 + 消融验证 | 低 | 可解释、可验证 |

## 6. 精确执行提示（通过审计后使用）

```markdown
目标：对 RAG 检索层（MemoryServiceImpl.searchContext / getRelevant）做深度重写，不扩功能面，
只在同一批输入上达到检索领域专业水准。

技术栈约束：Spring Boot 2.5.0 + 原生 HTML/JS + MySQL。
禁止引入 Lucene / Elasticsearch / 向量数据库 / 新 LLM 提供商。
只允许使用已有 AiClient（chat / chat(jsonMode) / embed）、现有表、纯 Java 数学。

沿用与不可破坏：
- diary_chat_log 表的 retrieved_chunks / retrieved_scores 语义不变
- companionStream 接口签名与 SSE 事件帧格式不变
- 不修改 shelf / archive / index 等非日记页

=== 必须交付 ===

（一）排序层
- 时间衰减：final = sim * exp(-Δt/τ)，τ=30 天
- 重要性融合：final = sim * (0.8 + 0.2 * importance/5)
- 分源配额：memory 40% / diary 40% / lore 20%

（二）召回层
- 纯 Java BM25 倒排（中文 2-gram，k1=1.2, b=0.75）
- RRF 融合 dense 与 BM25：score = Σ 1/(60 + rank_i)
- 查询改写：AiClient.chat jsonMode 产 2-3 子查询，embed 取均值；失败回退原始 query

（三）结果集合
- 语义去重：相似 > 0.92 合并保留最新
- MMR：λ=0.7，抑制同源近重复
- 相邻片合并：同 refId 且序号相邻的 chunk 拼接
- 去掉 chunkDiary 的「最多 8 片」硬截断

（四）性能
- 向量常驻内存 ConcurrentHashMap + 10min TTL + 写入时增量失效
- 检索 P95 ≤ 300ms

（五）可解释
- 检索日志扩展：候选集、各阶段分数、是否入选、是否被引用
- 每条结果附 relevance_confidence (high/medium/low)

（六）验证
- 金标准集 200 组，Recall@5 ≥ 0.80 / MRR ≥ 0.75 / nDCG@10 ≥ 0.75
- LLM-as-Judge 双盲 Δ ≥ 0.8，p < 0.05
- 消融每项 nDCG@10 下降 ≥ 0.03
- 下游引用准确率 ≥ 0.90，编造率 ≤ 5%

=== 禁止 ===
- 不得一次性全量上线，必须按 P1→P5 分期，每期可独立回滚
- 不得跳过消融与金标准集
- 不得为了新能力修改非检索层的既有签名
- 不得用「感觉更准」作为验收标准
```

## 7. 本阶段结论

- 选定模块：RAG 检索层（非新增功能）。
- 深度空间：排序信号、多样性、时间性、召回通道、分片策略、可观测性共 6 个维度均有明确缺口。
- 最大单点收益：**向量内存缓存**（延迟）+ **时间衰减/重要性融合**（排序合理性），均属低风险。
- 最大质量收益：**BM25+RRF 混合召回**（短查询如「我很烦」目前召回质量差）。
- 下一步：审计确认 → 按 P1 实现 → 每期用金标准集与消融数据验收。
